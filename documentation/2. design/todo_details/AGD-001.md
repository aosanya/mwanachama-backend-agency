# AGD-001 — Objective, Values/Rules, and RACI rescoping; Mission/Vision removed

Design session of 2026-09-10, run via the (adapted) `dev-research.md`
protocol. Started from: "how do goals, values and rules interact?" —
motivated by AI agents acting as `Role`s (the SWELab personas, AG7)
having no access to the tacit organizational knowledge a human Role-holder
would just know. See also
[../../1. requirements/insights-strategy-framework.md](../../1.%20requirements/insights-strategy-framework.md)
for the strategy-ontology background this grew out of.

## Decisions

1. **`Agency.Values []string` / `Agency.Rules []string`** (or richer
   objects — implementation detail, not decided here): cultural/strategic
   statements a human would treat as common knowledge but an AI agent
   needs made explicit. Examples given: "we prioritize correctness over
   speed," "never touch production data." **Plain text, informational
   only — no runtime enforcement.** Agency-wide scope. **Immutable: set
   once (creation/seed time), no edit path afterward, ever** — not even
   via the Draft lifecycle. This is a deliberately different posture from
   `Mission`/`Vision`'s current live-editability (AG11) — inheriting that
   editability was explicitly ruled out.

2. **`Objective` is new, first-class.** Originally specified 1:1 with
   `Goal`; **reversed 2026-09-10 (AG14)** — a `Goal` may have several
   `Objective`s, each one a granular unit a single `Role` is
   RACI-assigned to, so a Goal needing several roles' worth of work
   doesn't have to cram every RoleAssignment onto one Objective. Not a
   split of `Goal` into freeform sub-items — every `Objective` still
   requires a `GoalID`. Draft-scoped exactly like `Goal`/`Workflow`/
   `WorkItem`/`Role` (nullable `DraftID`, `""` = live; live rows
   immutable, must fork a Draft, edit the draft-scoped copy, promote — no
   exception).

3. **`WorkItem.GoalID` is removed entirely** (currently optional, `""` =
   untagged — see `models/workitem.go`). `WorkItem` now belongs to
   exactly one `Objective` (**required**, not optional — there is no more
   "untagged" `WorkItem`). `WorkItem.WorkflowID` ownership is unchanged
   and orthogonal to this.

4. **RACI moves to Objective-only.** `RoleAssignment.WorkItemID` (see
   `models/roleassignment.go`) becomes `RoleAssignment.ObjectiveID`.
   WorkItem-level RACI is dropped, not kept alongside. **Cross-repo
   impact**: `mwanachama-backend-api-kazi`'s K6 currently calls
   `ListRoleAssignmentsForWorkItem` directly (per this repo's own
   CLAUDE.md AG6 note: "the lookup K6 actually needs"). That resolution
   path becomes `WorkItem → Objective → RoleAssignments` — K6 needs its
   own follow-up, not assumed fixed by this row.

5. **Value/Rule, Objective-scoped**: optional `ObjectiveID` (empty =
   agency-wide, per decision #1). Same Draft-scoping/live-immutability
   rule as everything else in decision #2 — **plus new machinery**: a
   write (fork/edit/promote) to an Objective's Values/Rules is only valid
   if the caller holds the **Accountable** RACI label on that Objective.
   This is a **RACI-label-gated write-authorization check that doesn't
   exist anywhere in this codebase today** — every other write today
   gates at the gateway-capability level (`CapAgencyWrite`, per AG10),
   never per-RACI-label on a specific row. Confirmed explicitly not a
   bypass of the live-immutability rule (an earlier framing of this as an
   "Accountable can edit live" exemption was raised and explicitly
   rejected — "they are immutable").
   The gate covers Values/Rules only, not the Objective's own
   Title/Description.

6. **Mission and Vision are deleted, everywhere — confirmed explicitly
   ("delete them"), not a deprioritization.** This is a breaking,
   cross-repo removal of already-shipped, wired-up functionality:
   - `mwanachama-backend-agency`: `Agency.Mission`/`.Vision` fields
     (`models/agency.go`), whatever `agency.go`/`agency_impl.go` CRUD
     surface touches them.
   - `mwanachama-wakala-api` (AG11's identity feature): `Mission`/`Vision`
     appear in `internal/api/http/instance_handlers.go`,
     `internal/api/http/mcp_tools_agency.go`,
     `internal/api/http/mcp_tools_composite.go` (the **MCP tool surface**
     — i.e. the AI-agent-facing API also currently exposes Mission/Vision
     and needs updating, not just the human-facing HTTP handlers), and
     `cmd/server/selftest/selftest_create_agency_mission_vision.go`.
   - `mwanachama-wakala-studio`: `app/routes/agency-canvas.tsx`'s
     `IdentitySection` and `ALL_SECTIONS` (`'mission'`, `'vision'`),
     `app/routes/agency.new.tsx`'s `DRAFT_SECTIONS`,
     `app/components/WorkspaceMenu.tsx`'s `SECTION_ORDER`/`SECTION_LABELS`,
     `app/components/AgencyIdentityField.tsx`, and
     `app/api/instances.ts`'s `getAgencyIdentity`/`updateAgencyIdentity`.
   - Rationale given: Mission/Vision "add no value" now that Values/Rules
     exist to do the real work of making organizational context explicit
     for agents.

## Open, not decided here (flag for whoever implements)

- Where do Agency-wide Values/Rules actually get set, given they're
  immutable with no edit path? Nothing in this session named a
  creation-time API/UI for them — needs an implementation-time answer
  (e.g. set at `CreateAgency` time, or seeded per test fixture like
  SWELab/AG7).
- Exact `Value`/`Rule` field shape (single string vs. `{Title,
  Description}` struct) — not decided, left as an implementation
  choice.
- `Objective`'s own field shape beyond its `GoalID` link (does it
  carry `Title`/`Description`/`Ordinality` mirroring `Goal`, or something
  else) — not decided.
- Measure/Report (from the insights doc) are still out of scope — this
  session was Goals/Objectives/Values/Rules/RACI only.
- The RACI-Accountable write-gate (decision #5) needs a real design for
  *how* it's checked (session/auth plumbing needs to know the caller's
  identity maps to a `Role`, which nothing today requires) — flagged as
  new machinery, not specified further here.

## What reversing costs

Decisions #2–#5 (Objective/WorkItem/RACI rescoping) touch shipped,
tested code: AG3 (`WorkItem`/`Goal` models), AG6 (`RoleAssignment`), and
AG10's gateway wiring. Decision #6 (Mission/Vision removal) additionally
touches AG11 end-to-end (backend + MCP tools + frontend) in a sibling
repo already built against it. Reversing after implementation means
re-adding fields/routes/UI across three repos, not a local revert.
