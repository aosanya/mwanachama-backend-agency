# AGD-012 — A library of hazards, threats, consequences and controls; a bowtie is composed from it

Owner decision of 2026-10-31 (rows AG109, AG110, AG111). AGD-010 gave each risk
its own `risk_pathway` rows, so "supplier fails to deliver" written under three
risks was three rows, and AGD-011's controls could only stand on one copy. The
parts are now declared once, in a library under the draft, and a bowtie only
points at them.

## Objects

All five are draft-scoped (`draft_id` required), carry `created_at`,
`last_updated`, `deleted` where they are rows of their own, and mint their code
once in the creating transaction from the shared code sequence.

| Object | Code | Fields |
|---|---|---|
| `hazard` | `H-n` | `title` required; `description` |
| `threat` | `T-n` | `title` required; `description` |
| `consequence` | `Q-n` | `title` required; `description` |
| `control` | `C-n` | unchanged (AGD-011) |
| `risk_threat` | none | `draft_id`, `risk_code`, `threat_code`, `created_at` |
| `risk_consequence` | none | `draft_id`, `risk_code`, `consequence_code`, `created_at` |

`title` is unique among the live rows of one kind in a draft, compared without
case or surrounding space; a second one is refused (409). `risk` keeps `title`,
`top_event`, `owner` and the free-text `hazard`, and gains `hazard_code`: the
library hazard it names, optional, resolved by code. `hazard` text stays for
rows made before the library and for a risk whose hazard is not worth a row.

The link rows are addressed by code on both sides (AGD-003), so a fork never
strands one. A second link between the same risk and part in a draft is refused
by a unique index. `risk_pathway` stays declared until the consumers move
(AG101), then is deleted with its tools.

## Controls attach to library parts only

`control_attachment.target_type` gains `threat` and `consequence`; `target_code`
is a `T-n` or `Q-n`. `risk_pathway` stops being accepted on create and is kept
in the vocabulary only so a stored row still reads. `ValidForControl` accepts
`threat` and `consequence`.

A control is never attached to a bowtie. One control on a threat guards every
bowtie that uses that threat. Preventive or mitigating is still read, never
stored: a control on a threat prevents, one on a consequence mitigates. A bowtie
inherits the controls of the parts it uses, read through the links.

## Derived reads

- **Used in:** each hazard, threat and consequence reports `used_in`, the count
  and codes of the risks that use it (`hazard_code` for a hazard, the link rows
  for the others). Computed on read, never stored.
- **Controls on a part:** the `control_attachment` rows for its code.
- **Unguarded parts:** replaces `UnguardedPathways`. Every threat and
  consequence of the draft with no control attached, each with its `used_in`.
  Reported once per part, not once per bowtie. A part no risk uses and no
  control guards is listed too.
- **A bowtie's gaps:** its threats and consequences that are in the unguarded
  list.

## Delete is refused while in use

- A hazard named by any risk's `hazard_code`, a threat in any `risk_threat`, a
  consequence in any `risk_consequence`: refused with `ErrLibraryPartInUse`
  (409) naming the risks by code and title. Unlink first.
- A control still attached to a part is deleted as today (AGD-011), with its
  attachments.
- Deleting a threat or consequence that has controls attached removes those
  attachments in the same transaction, once no bowtie uses it.
- Deleting a risk removes its link rows, not the parts.

## Fork, document, hash, import

- A fork copies every library row and link row with fresh ids, codes and link
  codes kept; `hazard_code` is copied as written.
- The publication document gains `hazards`, `threats`, `consequences`,
  `risk_threats`, `risk_consequences`, in the import and export shape.
  `applyDocumentToDraft` restores them and raises the code sequence past `H-`,
  `T-` and `Q-` codes like it does for the others.
- The content hash covers all five.
- **Older documents:** `risk_pathways` still imports. Each pathway becomes a
  library `threat` (side `threat`) or `consequence` (side `consequence`) with
  the pathway's `title` and `scenario` as `description`, plus a link from its
  risk. Two pathways with the same title and side, across risks, become one part
  with two links. Controls attached to `risk_pathway` `RP-n` are re-targeted to
  the new part. Newly minted parts take `T-n`/`Q-n`; the old `RP-n` code is not
  kept. A document carrying both shapes imports once: a library part with the
  same title and side wins and the pathway only adds its link. A risk's free
  `hazard` text is left as text; no hazard row is invented.
- Export writes the new shape only.

## Issue scan

All `error` unless said:

- a link names a risk, threat or consequence that does not exist in the draft;
- a risk's `hazard_code` names no hazard;
- a control attachment names a `threat` or `consequence` code that does not
  exist, or a `risk_pathway` target (retired);
- `run_workflow` on a control attached to a threat (unchanged from AGD-011,
  retargeted from pathway to threat);
- a threat or consequence no risk uses: `warning`;
- a threat or consequence with no control: raises nothing, it is a gap on the
  unguarded list, not a publishing blocker (as AGD-011 for pathways);
- two live rows of one kind with the same title: `error` (the create refuses it,
  an import can still carry it).

| Tool | Route |
|---|---|
| `agency_create_hazard`, `agency_get_hazard`, `agency_update_hazard`, `agency_delete_hazard`, `agency_list_hazards` | `/hazards`, `/hazards/{hazard_id}` |
| `agency_create_threat`, `agency_get_threat`, `agency_update_threat`, `agency_delete_threat`, `agency_list_threats` | `/threats`, `/threats/{threat_id}` |
| `agency_create_consequence`, `agency_get_consequence`, `agency_update_consequence`, `agency_delete_consequence`, `agency_list_consequences` | `/consequences`, `/consequences/{consequence_id}` |
| `agency_create_risk_threat`, `agency_delete_risk_threat`, `agency_list_risk_threats` | `/risk-threats`, `/risk-threats/{risk_threat_id}` |
| `agency_create_risk_consequence`, `agency_delete_risk_consequence`, `agency_list_risk_consequences` | `/risk-consequences`, `/risk-consequences/{risk_consequence_id}` |
| `agency_list_unguarded_parts` | `/unguarded-parts` |

Lists of parts narrow by `code` and `title`; link lists by `risk_code` and the
part code. Get and list of a part include `used_in` and `control_codes`. Create
of a link takes codes, not ids, and refuses a code outside the draft (404) or a
second identical link (409). The existing `agency_*_risk` tools stay, with
`hazard_code` on create and update. Actions are `agency.hazard.*`,
`agency.threat.*`, `agency.consequence.*`, `agency.risk_threat.*`,
`agency.risk_consequence.*` and `agency.unguarded_parts.list`.

Errors: `ErrHazardNotFound`, `ErrThreatNotFound`, `ErrConsequenceNotFound`,
`ErrRiskThreatNotFound`, `ErrRiskConsequenceNotFound` answer 404;
`ErrInvalidHazard`, `ErrInvalidThreat`, `ErrInvalidConsequence` 400;
`ErrLibraryPartInUse` and `ErrLibraryTitleTaken` 409.

## Contract in code

The declarations are in `agency.blueprint.json` and `agency.agency.json`, the
carriers in `models/library.go` (`Hazard`, `Threat`, `Consequence`,
`RiskThreat`, `RiskConsequence`), `Risk.HazardCode`, and
`models.TargetTypeThreat` and `models.TargetTypeConsequence` in
`models/control.go`. Operations, impls, scan, fork, document and import are the
second wave.

## Amendment of 2026-10-31: a consequence belongs to one hazard

Owner decision. A consequence is what a hazard does when it is released, so a
consequence never stands alone. Threats stay free: one threat can lead to
several hazards.

- `consequence` gains `hazard_code`, **required**: the `H-n` it belongs to,
  resolved by code like every other link (AGD-003). Create and update refuse an
  empty code or one outside the draft (400 `ErrInvalidConsequence`, 404
  `ErrHazardNotFound`).
- A consequence has exactly one hazard. Two hazards with the same outcome are
  two consequences.
- The title rule narrows: unique among the live consequences of **one hazard**,
  not of the draft.
- A bowtie composes from one hazard. `agency_create_risk_consequence` refuses a
  consequence whose `hazard_code` differs from the risk's `hazard_code` (409),
  and refuses any consequence while the risk has no `hazard_code`. Changing a
  risk's `hazard_code` is refused while it links a consequence of another
  hazard.
- Deleting a hazard is refused while a consequence names it, as it already is
  while a risk does (`ErrLibraryPartInUse`, naming both).
- `used_in` of a hazard counts risks and consequences.
- The publication document, fork and hash carry `hazard_code` on each
  consequence.
- **Older documents:** a consequence made from a `risk_pathway` takes the
  `hazard_code` of its risk. When two risks that share the pathway title name
  different hazards, it becomes one consequence per hazard. When its risk names
  no hazard (free text only), the consequence imports without one and the scan
  raises an `error` on it: publishing is refused until the designer picks a
  hazard. The importer never invents a hazard row.
- **Issue scan:** a consequence with no `hazard_code`, or one naming no hazard,
  is an `error`; a linked consequence whose hazard differs from its risk's is an
  `error`.
- **Console:** the consequence form has a required Hazard select; the
  Consequences page shows the hazard on each row and filters by it; the bowtie's
  consequence picker lists only the risk's hazard's consequences, and a bowtie
  needs its hazard chosen first.
- **Risks reviewer:** the watch-list adds "a consequence that does not belong to
  the bowtie's hazard" and "a hazard with no consequence".
