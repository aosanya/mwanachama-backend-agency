# AGD-002 — Module catalog, Agency module-selection gates gateway routes, Objective↔Module cross table

Design session of 2026-09-13, run via the (adapted) `dev-research.md`
protocol. Started from: "the agency needs a model called available
modules... the agency can then select the modules it will use" — candidate
modules named across the session: `git`, `digitaltwin`, `taskmanager`,
`accounting`, `actor`, `assetmanager`, `comm`.

## Decisions

1. **Module selection is a real gate on gateway route registration, not a
   passive record** like `Value`/`Rule`. An unselected module's routes are
   genuinely absent — same shape as today's env-var-gated
   `DevOnlyRoutes`/`GitRoutes` pattern (the mux handler is simply never
   registered for that path prefix, a 404, not a 403 from a capability
   check).

2. **Full replace, not layered on top of the gateway's existing env
   vars.** Each candidate module already ships its own `routes/` package
   in its own repo — checked directly: `actor`, `assetmanager`, `auth`,
   `comm`, `custody`, `forms`, `git`, and `taskmanager` all have one;
   `digitaltwin` and `accounting` do not (see Open items below). The
   gateway's existing per-module env vars (`GIT_ROUTES`,
   `TASKMANAGER_ROUTES`, `AGENCY_ROUTES`) are superseded for these
   modules: whether the gateway mounts a module's `Routes(...)` is decided
   by that `Module`'s live `Enabled` state, read directly from the DB (the
   gateway already imports this repo as a plain Go library per AG10 — no
   network hop, no new coupling introduced). Non-module infra flags
   (`MCP_ROUTES`, `APPROVAL_ROUTES`, `DEV_ONLY_ROUTES`) are untouched —
   they aren't "modules" in this sense.

3. **`Module` catalog rows carry the selection state directly** (an
   `Enabled`-shaped field on `Module` itself) — no separate `AgencyModule`
   join table. Matches this repo's existing single-agency posture: no
   `AgencyID` column exists anywhere (`Department`/`Level`/`Role` all skip
   it for the same reason, confirmed AG3/AG5/AG6).

4. **`Objective`↔`Module` is a separate cross table, `ObjectiveModule`** —
   not a `ModuleID` column on `Objective` (`Objective` (`models/objective.go`)
   stays untouched). Free many-to-many: one `Objective` can reference
   several `Module`s, one `Module` can back many `Objective`s.

5. **`Module` is Draft-scoped** (nullable `DraftID`), following `Goal`'s
   lax rule: a live `Module` can be toggled directly, no forced
   fork→edit→promote cycle required. Considered and rejected:
   `Role`/`RoleAssignment`'s stricter live-immutability rule, which would
   have forced every module toggle through a Draft for review — the
   lighter Goal-shaped rule was chosen instead ("it follows the Goals for
   now").

6. **`ObjectiveModule` is also Draft-scoped**, and enforces the same
   same-scope rule AG6 established for `RoleAssignment`: a Draft's
   `Objective` can only link a `Module` that has itself been forked into
   that same Draft; a live `Objective` can only link a live `Module`.
   Cross-scope linking (a Draft's `Objective` referencing a currently-live,
   unforked `Module`) is not allowed — "for now," flagged as revisitable
   if it proves too strict in practice.

7. **`routes/module.go` + `mcp/module.go` are in scope for this pass** —
   confirmed 2026-09-14. `Module` gets the same AG9/AG13 treatment as
   every other domain type here (plain `net/http` route file, MCP tools
   closing over a `ManagerResolver`), not deferred as separate follow-up
   work.

## Open, not decided here (flag for whoever implements)

- **Catalog completeness**: `digitaltwin` and `accounting` exist as
  sibling repos but have no `routes/` package at all today — nothing for
  the gateway to conditionally mount yet. **2026-09-14: both repos now
  have their own board task to build one** — `accounting`'s
  [W14](../../../mwanachama-backend-accounting/documentation/3.%20implementation/todo.md)
  and `digitaltwin`'s
  [W11](../../../mwanachama-backend-digitaltwin/documentation/3.%20implementation/todo.md) —
  but neither is built yet, so until they land, `digitaltwin`/`accounting`
  selected in the `Module` catalog would still be a no-op at the gateway.
  Whether to list them in the catalog *now* (no-op until their routes
  land) or only once those tasks ship is still not decided here.
- **Catalog authorship**: not decided whether `Module` rows are seeded
  once (`SeedSWELab`-style) or created/edited live through routes/MCP by
  whoever administers the Agency.
- **Exact `Module` field shape** beyond `Code`/`DraftID`/`Enabled` (e.g.
  does it carry a `Name`/`Description`, or just a stable slug matching
  each sibling repo's own name like `"git"`/`"taskmanager"`) — not
  decided.
- **`liveContentHash`**: not decided whether it needs extending to cover
  live `Module` + `ObjectiveModule` rows. Existing precedent
  (`RoleAssignment`, `Value`/`Rule`, `Objective`) says yes — a module-only
  change should require republishing — but this session didn't confirm it
  explicitly.

## What reversing costs

Decision #2 (full replace of the gateway's per-module env vars) touches
shipped, working boot logic in `mwanachama-backend-api-gateway` for
git/taskmanager/agency specifically — reverting means restoring three
env-var checks in `main.go`. Decisions #4–6 (`ObjectiveModule` cross
table, Draft-scoping, same-scope rule) extend AG6's/AG12's already-shipped
Draft fork/promote machinery (`CreateDraft`'s per-type copy loops,
`PromoteDraft`'s delete-old-live/flip-to-live blocks) — reversing after
implementation means removing a table and its two copy-loop entries, not
a local revert.
