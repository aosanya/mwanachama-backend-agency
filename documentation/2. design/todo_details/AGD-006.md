# AGD-006 — There is no live; every row belongs to a Draft, publish reads from a Draft directly

> `ObjectiveModule`, named below among the draft-scoped tables, was removed by [AGD-008](AGD-008.md).

Design session of 2026-09-19, prompted by the user questioning the
`TrunkDraftID` sketch drafted as a follow-on to AGD-005: *"any draft can be
edited and published. why do we need a live version"*.

## The gap this closes

AGD-005 (2026-09-17) already renamed the mutable `draft_id IS NULL` row set
away from "live" — that word now means a channel on an `AgencyPublication`
tag — but it kept the row set itself, just relabeled as "the working set."
It still does two jobs no third tier needs to do:

- It's what `CreateDraft(forked_from_type: "live")` copies from.
- It's what `Role`/`RoleAssignment` (`ErrCannotEditLiveRACI`) refuse to edit
  directly, and what `PromoteDraft` merges a Draft's rows into — deleting
  the old working-set rows and minting new ids for the Draft's own rows in
  the process. That id-remint is the root cause AG6's own note already
  flagged: a `RoleAssignment.ObjectiveID` (or any cross-reference into the
  working set) goes stale on every promotion.

Every Draft is already fully self-contained — `CreateDraft`'s fork-copy loop
gives it its own Goal/Workflow/WorkItem/Role/RoleAssignment rows, not a
reference back to the working set. So a Draft never *needed* a privileged
sibling row-scope to be complete. The working set survived AGD-005 purely as
"what a new Draft forks from by default" and "what's protected from direct
edits" — neither of which requires the row-scope to exist, once nothing
downstream (AGD-005 decision #2: production reads the tag's JSON document
directly) actually depends on it for anything real.

## Decisions

1. **Every draft-scoped table's `DraftID` becomes non-nullable.** The eight
   tables AG16 gave a `Code` to that are also draft-scoped (`Role`, `Goal`,
   `Objective`, `Workflow`, `WorkItem`, `EventFlowStep`, `RoleAssignment`,
   `Value`, `Rule` — nine, `EventFlowStep` included), plus three more that
   share the identical nullable-`DraftID` shape without a `Code`:
   `Module`, `ObjectiveModule` (both walked by `CreateDraft`/`PromoteDraft`
   already), and `Issue` (AG26's scan-finding row, whose own doc comment
   already calls it "nullable ... like every other Draft-scoped row"). All
   twelve rows always name a real `Draft.ID`. No `""`/`NULL` sentinel,
   anywhere.
2. **`forked_from_type` drops `"live"`.** A new Draft forks from another
   Draft (`"draft"`, AG4's original case) or from a published tag (
   `"publication"`, AGD-005 decision #5) — never from a magic row-scope.
   Provisioning a brand-new Instance creates one empty Draft directly, not
   via any fork.
3. **The live-immutability rule is deleted outright**, not rephrased
   against a trunk pointer. `ErrCannotEditLiveRACI` and its callers
   (`UpdateRole`/`DeleteRole`/`UpdateRoleAssignment`/`DeleteRoleAssignment`)
   go away — every open Draft's rows are editable, always, because there is
   no longer a privileged row-scope to protect from direct edits.
4. **`PromoteDraft` is deleted, not repointed.** There is nothing left to
   promote *into*. `Draft.Status` collapses from
   `open`/`promoted`/`archived` to **`open`/`archived`** —
   `CanTransitionTo`'s `promoted` arm and every reference to it go with it.
5. **`PublishAgency` takes a `draftID` directly and publishes that Draft's
   own rows** — no merge step first. AG26's Issue scan already takes a
   `draftID` scope (`ErrDraftIDRequired` was already deleted by AGD-004
   itself), so the gate is unchanged; only its *caller* changes, from
   "scan whatever is live" to "scan the Draft named in the publish call."
   AG28's `buildDocument` serializes straight from that Draft's rows
   instead of from the working set. `ContentHash`'s no-op-publish guard
   compares against the target channel's *previous* document, not a
   separate live-content hash — same guard, simpler input.
6. **A published Draft is not auto-archived, and stays fully editable.**
   Publishing is a read of a Draft's current state, not a state transition
   on the Draft itself — the same Draft can be re-published (a new tag, or
   the same channel again) after further edits, or the operator can archive
   it by hand and fork a fresh Draft from the tag instead. Confirmed
   consistent with AGD-005 decision #4 (rollback re-channels an *archived*
   tag — a Draft's own open/archived status is orthogonal to any tag it
   produced).

## Migration

Every one of the twelve tables' existing `NULL`/`""`-scoped rows needs a
real `Draft` to belong to. Per existing Instance: mint one
`Draft{Description: "Migrated working set", Status: open}` and reassign
every `draft_id IS NULL` row across all twelve tables to it, in one
transaction, before the `NOT NULL` constraint is added — this is the same
shape `BackfillCodes` (AG16) already established for a different backfill
on nine of these same tables (`Module`/`ObjectiveModule`/`Issue` carry no
`Code` and never went through that backfill, but need this one same as the
rest). Existing rows with
`Status: promoted` (there may be none live, since `PromoteDraft` deleted the
promoted Draft's own rows on merge — its id lived on only as a spent
pointer) become `archived`; there is nothing to reinterpret in their row
content since promotion already discarded it.

## Open, deliberately

- **Which Draft does a fresh Studio session default to editing**, now that
  "the" working set no longer exists and `agency_list_drafts` may return
  several open Drafts with no ranking? A UI/UX question for
  `mwanachama-wakala-studio`, not a data-model one — this doc takes no
  position beyond "there is no longer a data-model answer."
- **Per-channel validation** (an AGD-005 open question) is unaffected and
  stays open.
