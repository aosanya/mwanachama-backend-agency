# AGD-005 — A publication carries the whole Agency; production runs off tags, not rows

Design session of 2026-09-16, immediately after AGD-004 shipped (AG26/AG27).
Started from the user challenging a cosmetic `scope: 'live' | 'draft'` field
added to the Studio's Issues panel: *"why do we need scope — we can have a
tag record with a json field that has all the agency info from which the
live/production agency can operate"*, then *"production only operates from
the tag table/model"*.

## The gap this closes

Today there are three tiers — Draft rows → live rows → `AgencyPublication` —
and **the publication stores no content**: only `ContentHash`, `Version`,
`Tag`, `Status`, `PublishedAt` (`publication_impl.go`). The consequences:

- Nothing can answer *"what was in v1"*. The hash proves **whether**
  something changed, never **what** it was. No rollback, no diff, no audit.
- `AgencySnapshot` — which sounds like it solves this — is an empty stub:
  `models/agencysnapshot.go` is `{DraftID, SnapshotAt}` and
  `draft_impl.go:478` writes one per promotion. Same receipt-not-snapshot
  shape.
- Production reads the **live rows**, which change the instant an operator
  edits a Role. Nothing running has a stable configuration, and publishing
  has no operational meaning whatsoever — it is a receipt for a change that
  already took effect at promote time.

The serialization this needs already exists and is proven: `POST
/instances/import` (`mwanachama-wakala-api`, decision #19) consumes a full
agency JSON document — every section, ids and Codes — and the 52 mined
templates under `developer/documentation/4. qa/agencies/` are written in it.
Publish producing exactly what import consumes is symmetric and costs no new
format.

## Decisions

1. **A publication carries the full Agency as JSON.** The tag record *is*
   the Agency, not a pointer to mutable rows. Shape: the existing
   import/export document (decision #19's), so publish → import round-trips.
   `ContentHash` stays as the no-op-publish guard it already is.

2. **Production reads that JSON directly** — not a materialized row cache.
   Chosen over "document is truth, rows are a cache" explicitly. One copy,
   no rebuild step, no possibility of document and rows disagreeing. The
   cost accepted knowingly: every consumer changes from a SQL query to a
   document read, and anything hot needs its own in-memory caching rather
   than leaning on the database.

3. **"Live" stops being a tier of rows and becomes a state on the tag** —
   the user's own reframing, better than any option offered. `Status`
   becomes `Channel`: a name (`"production"`, `"staging"`, …) or `""` for
   archived. **Several tags may be live at once on different channels**, and
   a channel name is unique across tags — at most one tag per channel.
   Publishing targets a channel and archives whichever tag held it. A
   consumer resolves the channel it runs against.
   - Modelled as a **column on the tag**, not a separate channel→tag pointer
     table and not a set-valued column — closest to the user's "a state in
     the tagged table", one table, no new concepts.
   - The mutable `draft_id IS NULL` row set is no longer "the live Agency".
     It is the **working set** — the design surface. All prose, doc comments
     and UI copy calling it "live" need retiring; that word now means a
     channel on a tag.

4. **Rollback is re-living an archived tag.** Set an archived tag's channel
   back and production is on it instantly, no rebuild. Requires relaxing
   `UpdatePublicationStatus`, which today permits only the one-way
   `active → archived` transition.

5. **A Draft may fork from the working set *or* from a named tag.**
   `CreateDraft`'s existing `forkedFromType` (`"live"`/`"draft"`) gains a
   third option — fork from a published tag, deserialising its document back
   into draft rows. This is what makes "go back to what v2 was and change
   one thing" possible, and it pairs with decision #4 rather than replacing
   it.

6. **`WorkPlan` and `ContextSource` are decommissioned outright** — code
   removed, tables dropped. The user's call: *"they are currently useless."*
   This was asked as "how do they reach production, since they sit outside
   the draft lifecycle entirely (AG8 — no `DraftID`, never forked, never in
   the import document's applied sections)"; the answer was that they should
   not. Evidence gathered before writing this down:
   - `mwanachama-wakala-studio` already hides `work_plan`
     (`ShortcutsMenu.tsx:25` excludes it) and excludes `ContextSource` from
     Search entirely (AG18's own note).
   - The only non-agency Go reference is
     `mwanachama-backend-taskmanager/events.go:183`'s `WorkPlanID`/
     `WorkPlanCode` **event-payload fields** — a reference to the concept,
     not a call into this library. Those become dead fields.
   - `MatchWorkPlans` has no external caller at all.

7. **`EventFlowStep` is explicitly kept** — "eventflow is important". Unlike
   WorkPlan it is Draft-scoped, already in the content hash, and rides into
   the published document naturally. AG26's dangling-`workflow_code` check
   stays.

## Open, deliberately

- **Validation timing.** AG26's scan reads rows. Does publish validate the
  working set and then serialize, or validate the document it is about to
  write? Assumed the former (no change to AG26) until something needs
  otherwise.
- **Per-channel validation.** Whether publishing to `"staging"` should be
  gated as strictly as `"production"` is unasked. Assumed identical.
- **Document size.** No limit is proposed. The mined templates are modest,
  and publications are infrequent, but nothing here bounds an Agency's
  growth.
- **What existing publications become.** Every current row has a hash and no
  document. They cannot be back-filled — the rows they described have moved
  on. Assumed they keep `Channel: ""` and are readable as history only.
