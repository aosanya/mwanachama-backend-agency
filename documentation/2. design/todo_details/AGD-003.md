# AGD-003 — Value/Rule multi-attach: Role/Goal/Objective/Workflow/WorkItem

> `ObjectiveModule`, named below as a precedent, was removed by [AGD-008](AGD-008.md); the reasoning here stands without it.

Design conversation with the user, 2026-09-15. Started from: "I want to
change Values and Rules to be attachable to Roles, Goals, Objectives,
Workflows and WorkItems" — today (AGD-001, AG12) a `Value`/`Rule` is either
Agency-wide (`ObjectiveID == ""`) or scoped to exactly one `Objective`, and
`ListValues`/`ListRules` don't even filter by that scope today.

## Decisions

1. **Scope widens from Objective-only to all five content types
   (Role/Goal/Objective/Workflow/WorkItem), and a single Value/Rule may be
   attached to more than one target at once** — e.g. the same Rule "never
   touch production data" attached to two `Role`s and a `WorkItem`
   simultaneously, not duplicated three times. Confirmed explicitly by the
   user over a single-scope-column design.

2. **Structural shape: a join table, not a column on `Value`/`Rule`.**
   `ValueRow`/`RuleRow` drop `ObjectiveID` entirely — they go back to being
   just `ID`/`Code`/`Text`/`DraftID`/timestamps. A new attachment table
   per type holds zero-or-more `(ValueID or RuleID, target type, target
   id)` rows. Zero rows = Agency-wide (carries forward AGD-001 decision
   #1/#5's meaning, just generalized from "`ObjectiveID == ""`" to "no
   attachment rows"). A single-column design (named FK columns, or one
   generic `ScopeType`/`ScopeID` pair) was considered and rejected — it
   cannot represent "attached to more than one target."

3. **Attachments are live-editable directly — not gated by the
   fork→edit→promote Draft cycle that governs a Value/Rule's own `Text`.**
   Confirmed explicitly by the user over the more conservative option
   (attachments inherit the same strict immutability as `Text`). Creating
   or deleting an attachment row against a *live* Value/Rule takes effect
   immediately, no Draft involved — even though editing that same Value's
   `Text` while live still requires the existing fork→edit→promote path.

4. **Consequence, not independently decided: attachments only ever
   reference live rows on both sides** (a live Value/Rule, and a live
   Role/Goal/Objective/Workflow/WorkItem) — a Draft-scoped copy of a
   Value/Rule (mid-`Text`-edit) carries no attachments of its own, and
   `CreateDraft`/`PromoteDraft` never fork or remap attachment rows at
   all. This actually **simplifies** the existing fork machinery rather
   than growing it: a Value/Rule's fork-eligibility check moves from a
   column test (`objective_id IS NOT NULL`) to an existence test against
   the attachment table (`EXISTS (SELECT 1 FROM <attachment table> WHERE
   value_id = ...)`), and the per-row `ObjectiveID` remap `CreateDraft`'s
   copy loop does today (`draft_impl.go:256`,`:272`) is deleted outright —
   there is nothing left to remap since attachments aren't copied.

## Open, not decided here (flag for whoever implements)

- **Ten narrow join tables vs. two polymorphic ones.** AGD-002 decision #4
  (`ObjectiveModule`) set a precedent in this codebase of a named table
  per type-pair over generic polymorphism. Followed literally here that's
  ten tables (`ValueRole`, `ValueGoal`, `ValueObjective`, `ValueWorkflow`,
  `ValueWorkItem`, and the same five for `Rule`) — each with a real typed
  FK-shaped column and its own index, consistent with `ObjectiveModule`
  and `ValueRow.ObjectiveID`'s own past precedent. The alternative is two
  tables (`ValueAttachment`, `RuleAttachment`) with a generic
  `TargetType`/`TargetID` pair — far fewer tables, and it absorbs a sixth
  attachable type later with no migration, at the cost of departing from
  the ten-table precedent and losing a per-type index/FK shape (a
  composite `(target_type, target_id)` index recovers most of that).
  Neither was chosen in this conversation.
- **Existence validation.** Nothing in this codebase's GORM layer puts a
  real foreign key across a cross-type reference (`ObjectiveModule`,
  `ValueRow.ObjectiveID` before this change, `RoleAssignment.RoleID`/
  `.ObjectiveID` are all "indexed, deliberately not an association").
  Whichever shape is chosen, each attach call must validate the target id
  actually exists (and is live) for its declared type in application
  code — the same pattern AG6 established for `RoleAssignment`'s
  same-scope check.
- **Write-authorization.** AGD-001 decision #5 already flagged that only
  an Objective's Accountable may write its Values/Rules as unbuilt
  machinery. Attach/detach reopens the same gap for the other four target
  types, and arguably more urgently: decision #3 above makes attach/detach
  an immediate live write, not something an operator reviews inside a
  Draft before promoting the way a `Text` edit is. Not designed here.
- **Create-time convenience.** Whether `CreateValue`/`CreateRule` should
  accept an optional initial target to attach in the same call, or always
  require a separate attach call afterward. Not decided.
- **List filtering.** `ListValues`/`ListRules` filter only on `Code`/`Text`
  today (`filters.go`) — there has never been server-side filtering by
  scope, even for the current single-`ObjectiveID` design. This task
  should add real filtering by each of the five target types (e.g. "every
  Value attached to Role X"), however the join table(s) end up shaped.
- **Agency-wide permanence, carried forward unchanged, not reopened.** A
  Value/Rule with zero attachments stays permanently un-forkable — same
  "no edit path, ever" rule AGD-001 set for `ObjectiveID == ""`, now keyed
  on "no attachment rows" instead. Nothing in this conversation asked to
  revisit that, including the edge case of a zero-attachment row gaining
  its first attachment live (decision #3) — whether that retroactively
  makes its `Text` forkable/editable is left to whoever implements, guided
  by the existing rule's intent rather than re-litigated here.

## What reversing costs

Touches AG12's already-shipped `Value`/`Rule` model end to end:
`models/value.go`/`rule.go`, `gormstore/value.go`/`rule.go`,
`value_impl.go`/`rule_impl.go`, `CreateDraft`/`PromoteDraft`'s Value/Rule
blocks in `draft_impl.go`, `filters.go`'s `ValueFilter`/`RuleFilter`,
`routes/value.go`/`rule.go`, `mcp/value_rule.go` — a schema and behavior
change to shipped code, not an additive-only feature. Reversing after
implementation means dropping the new attachment table(s) and restoring
`ObjectiveID` plus its old fork/remap logic, not a local revert.
