# AGD-011 — Controls replace Rules and Values

Owner decision of 2026-10-31, reached over a design conversation that began
from "what can we add to the agency to sell it to enterprise" and ended on one
object. A **Control** is a statement the agency commits to, optionally
enforced, optionally standing on a risk pathway. It replaces `rule` and
`value`. Nothing about a control is stored beside the agency definition: it is
drafted, published, forked and imported like a goal or a role (AGD-006,
AGD-007).

## Why one object

| Today | Problem |
|---|---|
| `rule` and `value` are plain text, attached to a role, goal, objective, workflow or step, and "informational only, nothing enforces them" (AGD-001) | Nothing makes them bind. A buyer asking "how do you know the agent obeyed it" has no answer |
| `riskmanager` declares a `control`, and a `barrier` places it on a pathway | The agency's own `risk` and `risk_pathway` (AGD-010) have no controls, and the riskmanager's control is a name and an owner with no link to anything enforcing it |
| An agency-wide value or rule has no edit path at all | Anything binding must be changeable through draft and publish, or it cannot be corrected |

"Control" is the word enterprise buyers, auditors and standards use. A plain
rule or value becomes an **advisory control**: text with no action. Nothing
else about it changes, and the role brief still shows it to the agent.

## What a control stores

| Field | Notes |
|---|---|
| `id`, `code`, `draft_id` | `code` is `C-<n>`, minted once and kept across forks, like every other code (AG16) |
| `text` | Required. What the agency commits to, and what the agent reads in the role brief |
| `action` | Optional. A name from the permission catalogue, such as `payments.release`. Empty means advisory |
| `condition` | Optional. `field`, `operator`, `value` over the tool's arguments, such as `amount > 5000`. Empty means every call to the action. One test only to start |
| `on_breach` | Required with `action`, refused without it: `block`, `hold_for_approval`, `flag` or `run_workflow` |
| `workflow_id` | Required with `run_workflow`, refused otherwise. A workflow in the same draft |
| `severity` | `low`, `medium` or `high`. Orders the gaps and the bowtie |

There is **no owner field**. Who manages a control is who holds the permission
to (see Permissions).

### Derived, never stored

| Read | Rule |
|---|---|
| Strength | `advisory` when `action` is empty; `enforced` when it has an action and an outcome; `tested` when it is enforced and a scenario of the draft passes against it |
| Preventive or mitigating | Read from the side of the pathway it is attached to. A control on a threat prevents, one on a consequence mitigates. A stored copy could disagree with the pathway, a read cannot |
| Who manages it | The roles whose permissions list the edit permission, and the people and agents who hold those roles |

## Where a control stands

A control attaches to the same targets a rule did (`role`, `goal`,
`objective`, `workflow`, `work_item`) and to one more: `risk_pathway`. No
attachment means agency-wide. The attachment is addressed by `code` on both
sides, as in AGD-003, so a fork never strands it.

**An attachment is a draft row.** AGD-003 made attaching live-editable, which
suited a note. For an enforced control it is a hole: detaching the control that
guards a pathway would weaken the agency with no draft and no publish. A control
attachment carries `draft_id`, is forked with the draft and travels in the
publication document. Detaching is a draft edit.

AGD-006 left no live row set, so AGD-001's permanent immutability of an
agency-wide rule has nothing to protect. It is retired: every control is edited
in a draft.

## What the scan refuses

`checkControls` in the Issue scan raises an `error`, so publishing is refused
with `ErrPublishValidationFailed`, when:

- `action` is not in the permission catalogue;
- `action` and `on_breach` are not both set or both empty;
- `on_breach` is `run_workflow` and `workflow_id` is empty or names no workflow
  in the draft;
- `run_workflow` is attached to a threat pathway (a workflow that runs after the
  event mitigates, it cannot prevent);
- an attachment names a control or target that does not exist;
- the control is enforced and no scenario of the draft passes against it. This
  is what makes "no rule goes live untested" true.

A risk pathway with no control is not an error. The bowtie shows it as a gap.

## Permissions

Two entries in `models/permissions_catalog.json`, held by roles like any other
permission (AG82):

| Code | Allows |
|---|---|
| `controls.edit` | Create, change, delete and attach controls in a draft |
| `controls.approve` | Publish a draft that changes an enforced control |

Authoring and approving are two codes so an agency can give them to different
roles. That separation of duties is the maker and checker an auditor asks for.
The check is the host's, on the tool call, the same place every other permission
is enforced. This replaces AGD-001's "only the Accountable may write", which was
never built.

The Review feature (`review.md`) is an AI design review of a draft, not an
approval, so it is not the home for this. The gate is on publish.

## Enforcement is the host's

This repo declares what a control says. The call happens in the host, so the
host evaluates it: before running a tool whose name is a control's `action`, it
tests the condition against the arguments and applies `on_breach`. It reads the
controls from the published document of the production tag (AGD-005), never from
the draft. Every outcome is logged with the control's `code`, and a test
scenario that expects a block is the evidence the scan looks for. The host side
belongs on the wakala-api board.

## Moving rules and values over

- Import reads `rules` and `values` from any older document and turns each into
  an advisory control. The 683 template files keep loading, and nothing is
  rewritten in bulk.
- A converted control keeps its old code (`RU-1`, `V-3`) as its code, so an
  attachment in a stored document resolves unchanged and no alias table is
  needed. New controls take `C-<n>`. A statement whose code a control already
  holds is dropped, so a document carrying both shapes imports once.
- Attachments on a converted rule or value convert with it, to the same
  targets, as draft rows.
- The role brief reads controls: one `Controls` list in place of the values
  and rules lists, and one section in the rendered text. A publication made
  before the change still carries `values` and `rules`, and the brief lists
  those after its controls.
- `rule` and `value`, their attachments, their tools and routes, and their
  scan checks are deleted last, once nothing reads them. AG74 (the permanent
  immutability hole) is superseded by that deletion.

## Other repos

Filed on their own boards, not here:

- **wakala-api:** the `agency_*_control*` tools and routes, the host-side
  evaluation and its log, the `controls.edit` and `controls.approve` gates.
- **studio and console:** a Controls page replacing Rules and Values, controls
  on a risk pathway, the strength label.
- **templates:** none to rewrite, because import converts. A re-mine can emit
  controls directly later.
- **riskmanager:** its `control` and `barrier` are not used by the agency. If
  the module is mounted later, a barrier should refer to an agency control by
  code. That is a decision for when it is mounted.
