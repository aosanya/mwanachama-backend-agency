# AGD-007 — The domain is declared, not written: agency adopts the catalog's blueprint/spec/operations format

Design session of 2026-09-24, prompted by the user pointing at
`mwanachama-backend-catalog` and asking for agency to be converted to "the
exact same format", with whatever is reusable lifted into
`mwanachama-backend-shared` because the other backends are next.

## What the format is

`mwanachama-backend-catalog` carries no row structs and no hand-written
route table. Three declarations and one generic engine stand in for them:

- **`catalog.blueprint.json`** — the *module's* declaration. It names the
  roles the module's own rules operate on (`entry`, `share_link`,
  `suggestion`, …) and, for each, the fields and indexes that mean the same
  thing in every domain. A role's field carries its type, whether it is
  required/unique/immutable/primary, its permitted values if it is an enum,
  a named validation pattern (`slug`, `json_object` — the name is the
  spec's, the meaning is the module's, registered in `patterns.go`), and a
  required prose description.
- **a domain spec** — the *domain's* declaration. It names the module it is
  written against, the domain, the instance prefix, and one object per
  table. An object that fills a module role inherits that role's whole field
  list and may override nothing but a default; an object with no role is
  storage the domain asked for and nothing else. `spec.Blueprint.Apply`
  refuses anything more adventurous than that.
- **`catalog.operations.json`** — the API's declaration. One entry per
  operation: method, path, the manager method it calls, its gating action
  (`<module>.<resource>.<verb>`), its HTTP status, a title and description,
  where each argument comes from (`path`/`query`/`body`, positional or
  `into` a struct field), and what it returns.

The engines are `spec` (validate, and emit the DDL — `Migrate` is the whole
storage story, no `AutoMigrate`) and `mwanachama-backend-shared/dispatch`
(turn declared operations into `httpwire.Route`s and into MCP tools, both by
reflecting the manager interface). `store.go` is the only storage code left:
it resolves which table plays which role, joins a declared field to a Go
field by name (`SubmittedBy` → `submitted_by`, deliberately not the json
tag), and refuses at construction if a declared column has nowhere to live
or a carried field is undeclared.

Physical names are `<instance>_<module>_<table>`, validated against a strict
alphabet because a table name reaches SQL as text and cannot be a bound
parameter, and measured against Postgres's 63-byte identifier limit, which
truncates silently rather than complaining.

## Decisions

1. **Agency converts completely, not just its storage.**
   `agency.blueprint.json` declares every object; an agency spec fills the
   roles; `agency.operations.json` declares all ~64 routes; `routes/`
   becomes `routes.go` + `tools.go` over `dispatch`, and the per-entity MCP
   tools are derived from the same operations spec. `gormstore/`'s row
   structs and the per-entity route and tool files are deleted. `models/`
   survives as thin carrier structs — the store still needs a Go type per
   role to read into. `mcp/composite.go` (`agency_design_from_spec`) and the
   dashboard UI stay hand-written: they are composites over several
   operations, not operations.

2. **`spec` and the generic store move to `mwanachama-backend-shared`.**
   The `spec` package already states it knows nothing about a catalog, so it
   moves as-is; `catalog/store.go` is generalized alongside it into a
   role-addressed store the modules share. Catalog then imports both rather
   than owning them, which is the only way the move is proved before fifteen
   more repos depend on it. What stays per repo is the JSON, the managers,
   and the domain rules.

3. **Agency adopts `<instance>_<module>_<table>`.** Today's names come from
   `gormstore.DefaultTableNames(instance)` — `<instance>_goals`. They become
   `<instance>_agency_goals`, with a rename migration and a matching update
   to the gateway's hand-maintained SQL mirror. This moves live tables in
   every deployment that has them, which is the cost of having one naming
   rule for all sixteen backends rather than two.

   Named concretely by the user, with the **mwanachama-2** Supabase project
   open: `agency_agency_goals` and its siblings should end up in that
   database, beside the `agency_catalog_*` tables the catalog module already
   has there. Same instance (`agency`), different module — which is the
   whole reason the module segment exists, since without it both modules
   would want `agency_agencies` and neither would notice.

4. **The format's reference documentation lives in
   `mwanachama-backend-shared/documentation/2. design/`**, with the engines,
   since it is an org-wide standard from here on. This repo keeps only the
   record of its own conversion.

5. **The first document in those tables is our own.**
   `developer/documentation/4. qa/mwanachama-wakala/agency.json` — Wakala
   written as an agency: 9 roles, 3 goals, 10 objectives, 4 values, 4 rules,
   8 attachments, 4 workflows, 16 work items, 35 role assignments, 10
   modules, 14 objective-module links. It is the most demanding document
   this repo has, so it is the acceptance check for the conversion rather
   than a nicety: anything it cannot round-trip is a finding about the
   format, not about the document. Its seven sibling module-config files
   stay out — its own README says they are proposed, and no agency-side
   module-config model exists to import them into.

## What this costs, and what it does not buy back

- `routes.ResourceNames` — the per-mount override letting a process address
  Goals under its own noun — has no equivalent in an operations spec, whose
  paths are literal. Nothing in the fleet is known to set it, but the
  capability goes away rather than being carried over.
- `routes.Route` is this repo's own struct with no `Action` field.
  `dispatch` emits `httpwire.Route`, which has one, so every agency route
  arrives gated for the first time and each mounting process sees a
  different type. Consumers to keep building: `mwanachama-backend-api-gateway`,
  `mwanachama-wakala-api`, `mwanachama-backend-api-kazi`,
  `mwanachama-backend-api-shared`, `mwanachama-backend-insights`.
- Nothing in catalog mints a `Code`. Agency's `NextCode` counter table and
  its per-entity-type sequence have no declared equivalent, so either the
  spec learns about sequences or the store keeps a hand-written helper —
  decided when AG39 gets there, not here. AG35 (the unguarded
  read-modify-write in that same helper) is a reason to rewrite it rather
  than port it.
- A field's prose description becomes required. Agency's field
  documentation currently lives in Go doc comments on the row structs; it
  has to move into the JSON, where the MCP tool schemas can read it.

## What the open questions turned out to be

Answered by AG37–AG42, and left here rather than deleted because the answer
is the useful part:

- **Draft scoping needed nothing.** `draft_id` is an ordinary required
  string with an ordinary index on all twelve objects; the scope is applied
  by the manager's own `scopeQuery`, which the store never had to know
  about.
- **The attachment tables are objects like any other**, each filling a role
  of its own, and so is the module catalog — the catalog is seeded by
  `Provision` from `models.ModuleCatalog`, which is Go data rather than
  anything declared.
- **Per-instance provisioning works, and it moved wakala-api's slug.**
  `SpecFor(instance)` is all a mount chooses, but the instance is a name
  segment now: wakala-api minted `"agy_" + uuid` — an underscore, and 36
  characters — so it mints `"agy" + 12 hex` instead, and a table set created
  under the old slug is orphaned rather than migrated. Registering the
  instance and provisioning its tables stay independent.
- **`AgencySnapshot` is not declared**, so nothing creates it and nothing
  drops it: `spec.Migrate` only ever adds. AG36 is now a decision about an
  inert table.
- **The import path is untouched** and wakala-api's suites pass against the
  converted shape. WK23 still sits on it, so a clean import is still not
  evidence that every reference resolved.

Two things the conversion changed that this record did not anticipate:

- **The two surfaces had drifted apart, and one declaration ends it.** MCP
  had deletes for Goal, Objective, Workflow and WorkItem that HTTP did not;
  HTTP had deletes for Value and Rule that MCP did not; the unnested
  capability-link listing existed only as a tool. Declaring the union gives
  the HTTP surface **four new DELETE routes** — which the gateway's Postman
  gate counts, taking it from 29 uncovered of 361 to 33 of 365 — and the
  tool surface six new tools. Nothing was removed from either.
- **Two published contracts had to be declared rather than derived**: a
  tool's name, because callers hardcode it, and the argument names behind
  the address, which is why every path wildcard is now `{goal_id}` rather
  than `{goalID}`.
